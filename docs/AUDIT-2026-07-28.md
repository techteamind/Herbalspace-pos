# Audit Menyeluruh Herbaspace POS — 28 Juli 2026

Audit ini: typecheck + build lokal (saya), + 5 agent review paralel (uang, keamanan,
offline/sync, inventori, laporan). Semua temuan sudah diverifikasi dengan membaca kode,
bukan tebakan. `file:line` bisa diklik.

**Jawaban singkat atas "apakah bisa jalan 100% tanpa bug?"** — Belum.
Kode **compile bersih** (`tsc` lulus) dan **build lulus**; jalur inti jual→void→poin
sudah benar setelah perbaikan P0/P1 terakhir. Tapi masih ada **backlog bug nyata**:
beberapa berpotensi **kehilangan uang / data** dan **celah keamanan**. Yang paling
mendesak: perbaikan terakhir **belum di-commit dan belum di-deploy**, dan ada
**migration DB yang hilang** sehingga DB baru langsung rusak.

Legend: 🔴 kritis · 🟠 tinggi · 🟡 sedang · ⚪ rendah

## Blocker Deploy / Infra (kerjakan DULUAN — tanpa ini yang lain tak berarti)

  idempotency, void restore, promo, WIB, SW) belum di-commit → belum ada di produksi.
- 🔴 **D2. Migration `client_ref` HILANG.** Kolom + unique index dideklarasikan di

## 🔴 Kritis — kehilangan uang / lockout / kebocoran lintas-tenant

- **C1. Penjualan offline menampilkan "Berhasil" palsu, no. struk `undefined`, tanpa
  indikator "menunggu sync".** `src/lib/api-client.ts:36`, `payment-sheet.tsx:139-173`,
  `pos/index.tsx:529`. Offline → `apiFetch` balikan `{_queued:true}`; `process()`
  memperlakukannya sebagai struk sukses (confetti, cart bersih, print no. "undefined").
  Kasir tak tahu transaksi cuma antre.
- **C2. Antrean offline replay pakai outlet/token saat SYNC, bukan saat capture.**
  `api-client.ts:34` menyimpan `headers:{}`; `offline-sync.ts:26-38` menempel outlet/token
  saat itu juga. Jual offline di Outlet A → owner pindah ke Outlet B / user lain login →
  reconnect → semua sale Outlet A tercatat di Outlet B / kasir lain. Omzet salah outlet.
- **C3. Logout meng-clear antrean → sale offline yang belum sync hilang permanen.**
  `AuthContext.tsx:90-91` `await clearQueue()` tanpa cek jumlah. Gabung dengan C1 (sale
  terlihat sukses) = jalur paling langsung menuju uang hilang diam-diam.
- **C4. RLS = kode mati; tak ada backstop DB.** `db/rls-policies.sql` menarget tabel/kolom
  yang tak ada (`organizations`, `org_id`, `raw_materials`) — skema asli pakai `tenants`,
  `tenant_id`, `ingredients`. Plus `db/index.ts:11-16` konek pakai service-role yang
  bypass RLS. Artinya isolasi tenant **hanya di kode app**; satu handler lupa filter
  `tenantId` = kebocoran instan.
- **C5. Owner terakhir bisa dinonaktifkan/di-demote → tenant terkunci permanen.**
  `employees.ts:81-102` PUT set `role`/`isActive` tanpa guard last-owner & tanpa self-guard.
  `role` juga tak divalidasi (string apa pun diterima). Recovery butuh edit DB manual.

## 🟠 Tinggi

- **H1. Re-save produk ber-varian meng-orphan optionIds → varian mati, harga dasar
  tertagih.** `variants.ts:64` selalu DELETE+INSERT (UUID option baru); edit produk tanpa
  buka VariantEditor mengirim optionIds lama yang lolos verbatim (`product-form.tsx:97-112`).
  Di POS `pos/index.tsx:277-282` tak ada varian yang match → fallback ke `product.price`.
  Terjadi hampir tiap edit-save biasa.
- **H2. Laporan cap 1000 transaksi / 100 pengeluaran, agregasi di klien → omzet
  understated, laba overstated.** `reports/index.tsx:37-38`, `transactions.ts:12`,
  `expenses.ts:28`. Periode "Tahunan"/"Bulanan" ramai > cap → angka uang diam-diam salah.
  Fix nyata: agregasi di server (SUM/GROUP BY), bukan menaikkan cap lagi.
- **H3. share-receipt: selalu 401 (fitur rusak) + bocorkan COGS/PII lintas-tenant +
  layani struk void.** `share-receipt.ts:31-60` dibungkus `createHandler` yang meng-auth
  semua method → link publik selalu 401; handler abaikan tenant, kembalikan `unitCogs`
  (margin), PII customer, payments, cashier; tanpa filter `status`.
- **H4. Jaringan flaky tak masuk antrean (hanya saat `navigator.onLine===false`).**
  `api-client.ts:29`. Sinyal lemah (onLine tetap true) → fetch throw → sale tak diantre,
  kasir tak bisa menyelesaikan. Fix: antre saat fetch gagal, bukan hanya cek flag.
- **H5. Ganti satuan bahan tak konversi stok/resep/harga.** `ingredients.ts:43` +
  `ingredient-form.tsx:32-36`. gram→kg: stok, qty resep, `lastCost`, COGS semua salah
  faktor konversi.
- **H6. Stock adjust read-modify-write non-atomik → lost update.**
  `stock-movements.ts:25-45` baca stok ke JS lalu tulis; dua adjust bersamaan saling timpa.
  (Bandingkan `create_sale` yang atomik.)
- **H7. Catatan item tak pernah disimpan.** Tak ada kolom `note` di `transaction_items`
  (`schema.ts:178-192`) dan `create_sale` tak insert, padahal klien kirim `note`
  (`payment-sheet.tsx:152`). Reprint dari riwayat kosong.
- **H8. Link struk WA = `localhost` di APK.** `pos/index.tsx:499`, `detail.tsx:59` pakai
  `window.location.origin` → di Capacitor = `http://localhost` → link mati bagi pelanggan.
  Butuh base URL publik dari env.
- **H9. Tutup shift dengan shift null-outlet menjumlah SELURUH tenant.**
  `shifts.ts:78,92` tanpa filter outlet saat `outletId` null → rekonsiliasi kas ngawur
  di tenant multi-outlet.
- **H10. Kasir bisa menutup shift kasir lain / outlet lain.** `shifts.ts:55-64` PUT
  `close` cari by `id`+`tenantId` saja, tanpa `requireRole` & tanpa cek `cashierId`.

## 🟡 Sedang

- **M2. `/me` gagal → `role` null seluruh sesi (offline), tanpa retry.**
  `AuthContext.tsx:55-63` `catch(()=>{})`; GET tak diantre offline → semua layar role-gated

- **M3. Dua shift aktif bisa balapan (TOCTOU, tanpa constraint DB).** `shifts.ts:35-41`

- **M11. `X-Outlet-Id` tak divalidasi milik tenant.** `auth.ts:111-117` owner-supplied

## ⚪ Rendah

- **L1. Arti "return" tak konsisten:** tulis = stok keluar (`stock-adjust-form.tsx:25-26`),
  tampil = "in" hijau (`stock-movements/index.tsx:11-14`).
- **L2. Thermal UTF-8 mojibake** untuk karakter non-ASCII (`thermal-printer.ts:5-8`);
  tak set code-page ESC/POS.
- **L3. `product.costPrice` snapshot basi** vs COGS live setelah `last_cost` berubah
  (`recipes.ts:46-49`). (COGS transaksi tetap benar.)
- **L4. Back-arrow Shift mati saat loading** — `shifts/index.tsx:15` guard `history`
  (data list), bukan browser history.
- **L5. Gagal buka shift senyap** — `shifts/index.tsx:101-104` tanpa error UI (409 tak
  ditampilkan).
- **L6. IDOR-lite:** `modifierGroupId`/`ingredientId`/`optionIds` dari klien tak dicek
  milik tenant (`product-modifiers.ts:17`, `recipes.ts:34`, `variants.ts:64`). Dampak
  minor karena parent tenant-scoped.
- **L7. Diskon tanpa validasi promo & tanpa role gate** (`sales.ts:41`). Ter-clamp
  `[0,subtotal]`, jadi bukan lubang baru, tapi kasir bisa nol-kan sale.

## Sudah BENAR (pernah dicurigai, terverifikasi bukan bug)

- Jual→void: gate atomik `status <> 'void'`, restore stok dari movement tercatat, poin
  dibalik + clamp `GREATEST(...,0)`. `transactions.ts:47-93`.
- Idempotency `client_ref`: advisory lock + replay lookup di `create_sale`. Aman dari
  double-charge saat retry.
- Math uang klien vs server: tax `round(afterDiscount*pct/100)` konsisten; promo tak
  di-stack (ambil terbesar) & di-cap subtotal.
- SW stale bundle di APK: di-unregister + reload di native, registrasi hanya web.
- Dashboard batas hari WIB, weekly `AT TIME ZONE 'Asia/Jakarta'`.
- change-password aman (verifikasi current; owner reset tenant-scoped, blok reset owner
  lain). PDF export XSS aman (`escHtml`). Error handler tak bocorkan SQL di produksi.
